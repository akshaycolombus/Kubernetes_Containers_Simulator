Chapter One

The Foundation: Infrastructure vs. Kubernetes Software

Architecture 101

Beginners often confuse hardware / virtual machines with Kubernetes components. A Kubernetes cluster is simply a fleet of standard Linux servers (virtual machines or bare-metal) connected via a physical network, running specialized daemon processes that coordinate together.

The Control Plane (Master Node)

The brain of the cluster. It makes global decisions (e.g., scheduling pods, detecting failures, maintaining desired state) and responds to cluster events.

Worker Nodes (Data Plane)

The muscle of the cluster. These Linux machines run your actual containerized workloads, manage network routing at the host level, and monitor container health.

Chapter Two

The Workload Hierarchy

Mental Models

How does Kubernetes manage applications without forcing you to manually configure containers on specific servers? The secret is the Workload Hierarchy (the Russian nesting doll model of declarative state).

1. Deployment
Desired State & Rollouts

Declares what should run (e.g. replicas: 3, image v1.2) and manages progressive zero-downtime rolling updates.

Kind: Deployment
2. ReplicaSet
Headcount Enforcer

Continuously counts active pods matching its label selector. If count < desired, it spawns new pods immediately.

Kind: ReplicaSet
3. Pod
Shared Sandbox

The atomic unit of scheduling. Shares a single IP address, localhost loopback, and optional volume mounts across containers.

Kind: Pod
4. Container
Isolated Linux Process

The actual user binary executing inside Linux cgroups (resource caps) and namespaces (isolated PID, mount).

Process: Node.js / Go
Interactive Deployment Manifest (Click lines to inspect bindings) deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
name: web-frontend
spec:
replicas: 3 # 👈 ReplicaSet headcount
selector:
matchLabels:
app: web-store
template: # 👈 Pod Blueprint starts here
metadata:
labels: { app: web-store }
spec:
containers:
- name: nginx-server
image: nginx:1.25-alpine
ports: [{ containerPort: 80 }]
spec.replicas: 3

The Deployment tells its child ReplicaSet to ensure exactly 3 healthy Pod instances running at all times. If a node crashes, the ReplicaSet replaces it immediately.

💡 Pro Tip: Never create naked Pods directly in production—always wrap them inside a Deployment so they self-heal.
Click any line to see how selectors wire Pods

Deployments vs. StatefulSets (Stateless vs. Stateful)

Feature Deployment (Stateless) StatefulSet (Stateful)
Pod Identity Random hash (e.g. web-7b9d-a1x9) Stable Ordinal (db-0, db-1, db-2)
Interchangeability 100% interchangeable; any pod can handle any web request Specific roles (e.g., db-0 is Leader, db-1 is Replica)
Persistent Storage Shared volume (ReadWriteMany) or ephemeral disk Dedicated PersistentVolume per ordinal pod via VolumeClaimTemplates
Startup / Teardown Concurrent (all at once) Strictly Sequential (0 → 1 → 2 on startup, reverse on scale-down)
Ideal Workloads Web APIs, React Frontends, Stateless Microservices PostgreSQL, Kafka, Redis Cluster, Elasticsearch

Chapter Four

Networking & Services

Virtual IPs & Routing

Every Pod gets its own IP address. However, Pods are ephemeral: when a Pod crashes or a Deployment updates, the old Pod is destroyed and a brand new Pod is born with a different IP address.

A Service solves this by providing a permanent, stable virtual IP (ClusterIP) and internal DNS name that automatically load-balances traffic across all healthy matching Pods.

ClusterIP (Default)
Internal-Only Virtual IP

Reachable only from inside the cluster. Implemented via Linux kernel iptables or IPVS rules programmed by kube-proxy.

Scope: Intra-cluster
NodePort
High-Port Host Exposure

Opens a dedicated high port (range 30000-32767) on every worker node's external IP and routes traffic to the Service.

Port: 30000-32767
LoadBalancer (ELB)
Cloud Edge Integration

Instructs cloud providers (AWS, GCP, Azure, IBM Cloud) to provision an external public Load Balancer directing traffic to your NodePorts.

Scope: Public Internet
Lab Spotlight: Port Translation Unpacked kubectl expose
$ kubectl expose deployment/web-store --type=NodePort --port=80 --target-port=8080
--port=80 The virtual port the ClusterIP Service listens on inside the cluster network.
--target-port=8080 The internal port where the Container process is listening inside the Pod.
NodePort :31456 The automatically assigned high port opened on every Worker Node host VM.

Chapter Five

Complete Request Lifecycle: Management vs. Data Plane

Two Parallel Universes

A major beginner pitfall is assuming all requests go through the API server. In reality, Kubernetes operates with two completely separate request planes:

1. Management Plane (Control Plane Requests)

Used by engineers & CI/CD pipelines to create, scale, or inspect resources.

1 kubectl scale deployment web --replicas=5
2 kube-apiserver checks Authentication & RBAC permissions
3 Persists desired state to etcd
4 Deployment Controller notices drift & generates new Pod specs
2. Data Plane (End-User HTTP Traffic)

Used by actual customers buying products or loading web pages. Bypasses API server and etcd completely!

1 End-user browser requests https://myapp.com/checkout
2 Hits Cloud Load Balancer → NodePort on Worker VM
3 Kernel iptables/IPVS rewrites destination IP to active Pod IP
4 Web server container inside Pod processes request & returns 200 OK

Chapter Six

Troubleshooting & Resiliency Matrix

Failure Recovery

Kubernetes is built for failure. Hardware dies, kernels panic, and memory leaks happen. Here is how the cluster handles failures at every layer:

Failure Level Root Cause Impact Kubernetes Auto-Remediation
Container Crash Unhandled exception, OOMKilled (Exit 137) Temporary pod downtime Kubelet automatically restarts container with exponential backoff.
Pod Deletion Accidental `kubectl delete pod` 1 replica lost ReplicaSet controller detects count (2 < 3) and spawns replacement in milliseconds.
Worker VM Crash Power loss, kernel panic, hypervisor crash All pods on that node unreachable Node Controller marks node NotReady, evicts pods, and Scheduler recreates them on healthy nodes.
Control Plane Outage API server down, master network cut No `kubectl` commands, no auto-scaling Data Plane continues uninterrupted! Existing containers on worker nodes keep serving user traffic!
